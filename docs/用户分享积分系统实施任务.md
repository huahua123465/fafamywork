# 用户分享积分系统实施任务

## 1. 项目目标

在不影响现有公开浏览体验的前提下，为网站增加普通用户账号、专属分享链接、有效访问积分、用户积分中心和管理员积分控制能力。

核心原则：

- 游客浏览首页、项目列表、项目详情、截图、购买说明和提交咨询时，不要求注册或登录。
- 游客可以普通分享页面，但普通分享不产生积分。
- 用户只有在选择“分享赚积分”时才需要注册或登录。
- 接收分享链接的访客不需要注册或登录。
- 分享积分由服务端根据有效访问判定，前端不能直接增加积分。
- 管理员账号与普通用户账号完全分开，保留现有 `/admin` 管理密码体系。
- 项目卡片、详情首屏和分享内容继续使用总览拼图，不改成单张截图。

## 2. 第一版业务规则

第一版按以下规则实现，管理员可以在后台修改其中的积分参数：

| 规则 | 默认值 |
| --- | --- |
| 分享积分总开关 | 开启 |
| 每次有效访问奖励 | 5 积分 |
| 每位分享者每日最大奖励次数 | 10 次 |
| 有效访问最短停留时间 | 15 秒 |
| 同一访客去重周期 | 30 天 |
| 注册奖励 | 默认关闭，0 积分 |
| 分享者访问自己的链接 | 不奖励（含退出登录、换浏览器：分享者 7 天内用过的网络、用过的浏览器都算本人） |
| 机器人或自动化访问 | 不奖励 |
| 积分用途 | 第一版只累计和展示，不开放兑换 |

一次有效访问必须同时满足：

1. 访客通过包含有效 `ref` 分享码的链接进入。
2. 分享用户存在、状态正常，分享积分功能处于开启状态。
3. 访客不是分享者本人。
4. 访问不是已识别的爬虫或自动化请求。
5. 页面停留达到管理员设置的时间。
6. 访客产生至少一次真实交互，例如滚动页面、查看截图或进入其他页面。
7. 在去重周期内，同一访客没有给同一分享者产生过奖励。同一网络（IPv4 地址 / IPv6 的 /64 网段）或同一浏览器设备号都视为同一访客，换 UA 不算新访客；代价是同一办公室、同一家庭 WiFi 下的多位好友 30 天内只计一次。
8. 访客的网络或浏览器设备号不属于分享者本人（开始访问时和确认时各查一次）。
9. 分享者当天尚未达到最大奖励次数。

点击“分享赚积分”本身不发积分。只有其他访客形成有效访问后，服务端才发放积分。

## 3. 用户流程

### 3.1 游客浏览

```text
进入网站 → 浏览项目 → 查看截图或购买说明 → 无需登录
```

### 3.2 游客普通分享

```text
点击普通分享或复制地址 → 分享当前页面普通链接 → 不登录、不计积分
```

### 3.3 游客选择分享赚积分

```text
点击“分享赚积分”
→ 检查登录状态
→ 未登录时打开登录/注册弹窗
→ 登录成功后自动继续原分享操作
→ 获取专属链接
→ 调用系统分享或复制链接
```

登录弹窗需明确提示：浏览网站不需要登录，只有分享赚积分需要账号；用户也可以选择“暂不登录，普通分享”。

### 3.4 登录用户分享

```text
点击“分享赚积分”
→ 服务端生成或返回专属分享链接
→ 显示本次奖励规则与今日剩余次数
→ 调用系统分享；不支持时复制链接
```

专属链接示例：

```text
https://网站域名/projects/smart-todo?ref=AB7K29
```

### 3.5 被分享者访问

```text
打开带 ref 的链接
→ 正常浏览，无需登录
→ 服务端创建待确认访问记录
→ 达到停留和交互条件
→ 前端提交有效访问确认
→ 服务端完成去重、限额和风控校验
→ 给分享者增加积分并写入积分流水
```

## 4. 页面与交互范围

### 4.1 全站顶部导航

- 未登录时显示轻量“登录”入口。
- 已登录时显示昵称或头像入口和当前积分。
- 移动端入口放入展开菜单。
- 不把注册设为主导航项，注册在账号弹窗中完成。

### 4.2 登录和注册弹窗

- 支持登录与注册模式切换。
- 注册字段：用户名、昵称（可选）、密码、确认密码。
- 登录字段：用户名、密码。
- 登录成功后恢复用户刚才准备执行的分享操作。
- 提供“暂不登录，普通分享”选项。
- 展示清晰的校验错误、限速提示和登录过期提示。

### 4.3 项目详情页分享入口

- 在现有主要操作区域增加“分享赚积分”。
- 分享面板显示项目总览拼图、项目名称、奖励规则、今日剩余奖励次数。
- 支持系统原生分享和复制专属链接。
- 分享素材继续使用总览拼图。

### 4.4 用户中心 `/account`

- 当前积分余额。
- 累计有效分享次数。
- 今日奖励进度。
- 用户专属分享码。
- 最近积分流水。
- 最近分享访问记录。
- 修改密码。
- 退出登录。
- 第一版使用昵称首字母头像，不增加头像上传。

### 4.5 管理后台 `/admin`

保留现有资料、留言和统计功能，并增加：

1. 积分规则设置
   - 分享积分开关。
   - 每次有效访问奖励。
   - 每日奖励次数上限。
   - 有效停留秒数。
   - 同一访客去重天数。
   - 注册奖励开关及奖励数值。
2. 用户管理
   - 搜索和查看用户。
   - 查看注册时间、状态、积分和有效分享次数。
   - 封禁或解封用户。
3. 积分管理
   - 查询积分流水。
   - 管理员手动增加或扣除积分。
   - 调整积分时必须填写原因。
   - 撤销异常分享奖励。
4. 操作审计
   - 记录管理员修改积分规则、用户状态和积分的操作。

## 5. 账号与安全规则

- 第一版使用用户名和密码注册，不强制手机号或邮箱。
- 用户名唯一并限制长度及允许字符。
- 密码至少 8 位。
- 密码只保存安全哈希，不保存明文。
- 普通用户登录会话和管理员 token 使用不同的签发与校验逻辑。
- 登录、注册、分享访问和有效访问确认接口均需限速。
- 注册接口使用蜜罐字段和频率限制阻止简单机器人。
- 用户被封禁后不能登录、创建积分分享或继续获得积分。
- 会话 token 在数据库中只保存哈希。
- 忘记密码第一版由用户联系管理员处理，不实现邮件找回。

## 6. 数据存储方案

用户、会话、分享记录和积分使用 SQLite，不继续写入普通 JSON 文件。数据库存放在服务器持久化目录：

```text
/root/fafamywork/deploy/data/app.db
```

计划数据表：

### 6.1 `users`

- `id`
- `username`
- `nickname`
- `password_hash`
- `referral_code`
- `points_balance`
- `status`
- `created_at`
- `last_login_at`

### 6.2 `user_sessions`

- `id`
- `user_id`
- `token_hash`
- `expires_at`
- `created_at`
- `last_used_at`

### 6.3 `share_visits`

- `id`
- `sharer_user_id`
- `referral_code`
- `project_slug`
- `visitor_hash`
- `status`
- `created_at`
- `qualified_at`
- `reward_points`

访问状态包括：`pending`、`qualified`、`rewarded` 和 `rejected`。

### 6.4 `point_transactions`

- `id`
- `user_id`
- `amount`
- `balance_after`
- `type`
- `reference_id`
- `reason`
- `operator`
- `created_at`

流水类型包括：`share_reward`、`register_bonus`、`admin_add`、`admin_deduct` 和 `reward_revoke`。

### 6.5 `point_settings`

- `points_per_qualified_visit`
- `daily_reward_limit`
- `qualification_seconds`
- `visitor_dedupe_days`
- `registration_bonus`
- `updated_at`

### 6.6 `admin_audit_logs`

- `id`
- `action`
- `target_user_id`
- `before_value`
- `after_value`
- `reason`
- `created_at`

积分余额更新和积分流水写入必须在同一个数据库事务中完成。有效访问确认必须幂等，同一访问重复提交不能重复奖励。

## 8. 防刷与一致性要求

- 前端不能传入应奖励的积分数，奖励值只能由服务端配置决定。
- 分享者本人不能给自己贡献积分。
- 同一访客在去重周期内只能给同一分享者贡献一次。
- 同一访问记录重复确认只能处理一次。
- 同一 IP 短时间大量请求触发限速。
- 每个分享者执行每日奖励次数上限。
- 被封禁用户不能继续获得奖励。
- 爬虫和明显自动化请求不创建奖励。
- 不长期保存原始 IP；使用带服务端密钥的不可逆摘要进行去重。
- 管理员调整积分必须填写原因并记录审计日志。
- 撤销奖励通过反向积分流水完成，不直接删除历史流水。

## 10. 每一步的确认格式

每个任务完成后，报告至少包括：

1. 本步完成了什么。
2. 修改了哪些文件。
3. 执行了哪些测试以及结果。

未收到用户继续指令前，不主动进入下一项任务；但为完成当前任务所必需的测试、修正和复核应一次完成。

## 11. 代码与内容约束

- 不手动修改 `src/content/new-projects.json` 或其他由同步脚本生成的同名数据文件。
- 项目文案修改使用 `src/content/project-copy.json`。
- 中文不设置 `letter-spacing`。
- 正文行高使用无单位 `1.8`。
- 标题行高使用无单位 `1.45`。
- `body` 不使用像素行高。
- 字重只使用 `400` 和 `600`。
- 卡片、首屏封面和分享卡片保持总览拼图。
- 不使用 `git reset --hard`。
- 不丢弃用户已有修改。
- 不强制推送。
